RV32I, end to end

This is the whole project rebuilt as a course, starting from ordinary digital-design knowledge and going all the way to a pipelined RISC-V core verified against a third-party reference model. Where the original design guide is a running log, this reorganizes the same material by concept, and adds the diagrams and the real captured data.

Chapter 00

Orientation

Three things exist in this project, and almost everything interesting is about the relationship between them.

  1. The core — a 5-stage pipelined RV32I CPU in SystemVerilog (rtl/), M-mode only, with CSRs, synchronous traps, a timer interrupt, a memory-mapped UART, and external-debug halt/resume.
  2. A reference model — something that says what the correct answer is for a given program. This used to be a hand-written C++ instruction-set simulator; it is now Spike, RISC-V International's own reference simulator.
  3. Test programs and testbenches that run the same program on both and diff the result.

The hard-earned lesson of this whole project is that step 3 is never as simple as "run both, diff the answer." A comparison between two models is only meaningful within the region where the two models are actually comparable, and that region has to be built and defended deliberately — see Chapter 07 and Chapter 08 for exactly how many ways that went wrong before it went right.

You said you know ordinary digital design but not this project specifically. This course assumes you can read a schematic, know what a flip-flop and a mux are, and have seen a state machine — and builds everything project-specific on top of that footing.

Chapter 01

From single-cycle to pipeline

The single-cycle core is the version everyone's ordinary digital design course already resembles. The pipeline is what turns that into something worth writing a verification environment for.

The single-cycle baseline

One clock edge, one instruction, start to finish: fetch → decode → read the register file → ALU → touch memory → write the register file, all as one combinational path between two edges of the clock. Simple to reason about, because every instruction sees a machine that is completely settled — no other instruction is ever partway through. The cost is the clock period: it has to be long enough for the slowest instruction's entire path, load-to-writeback, every single cycle.

Splitting it into five stages

Pipelining cuts that one long path into five short ones and puts a register between each:

Same total work per instruction, but each stage is roughly a fifth the length, so the clock can run roughly five times faster. Five instructions are now in flight at any instant — and that's the catch. Instruction N+1 reads its registers in ID while instruction N is still sitting in EX, hasn't computed a result yet, and certainly hasn't written it back. That's a hazard, and it is worth internalizing precisely why the single-cycle version never had one: every one of its instructions saw a fully settled machine, because there was never more than one instruction alive at a time. Chapters 03 and 04 are the whole story of what has to be added to make five simultaneous, mutually dependent instructions behave as if they ran one at a time.

Architecture: Harris & Harris naming, four states of “done”

This core follows the Digital Design and Computer Architecture convention of suffixing every signal with the stage it belongs to — PCF, InstrD, ALUResultE, ReadDataM, ResultW. That is not cosmetic. With five instructions live, "the instruction I'm talking about" is ambiguous unless the signal name says which one.

The two instructions that never touch the ALU the normal way

LUI bypasses the ALU's normal two-operand path entirely: aludec forces ALUOP_LUI_PASSTHRU, which selects ALU op 1010 (PASSB) — result = b, i.e. the immediate passed straight through. That's a smaller change than it looks: the alternative (a dedicated 4th writeback-mux source, threaded through three extra pipeline register stages just for one instruction) is real added hardware for no benefit, since the ALU's B input was already available.

AUIPC instead swaps the ALU's first operand: a mux (AUIPCSel) selects PCE instead of the forwarded register value as SrcAE, then the ALU does a completely ordinary add against the immediate.

Where each control transfer resolves

This is the single decision with the most downstream consequences in the whole pipeline — it drives half of Chapter 04.

  • Branches and JALR resolve in EX. They need forwarded operands (a branch may compare against a value the immediately preceding instruction produced), or for JALR, an actual register value — neither is available combinationally in ID.
  • JAL resolves in ID. Its target, PC + imm, has zero register dependency, so there is no reason to wait for EX.

The consequence is the number of already-fetched, wrong-path instructions that have to be thrown away — see the flush comparison diagram in Chapter 04.

Chapter 03

Three hazards

Every hazard in a pipeline reduces to one of three flavors, and each has exactly one correct fix. Using the wrong fix for the wrong flavor is where most of the bugs in Chapter 08 came from.

Data hazard — forward it

ADDI x1,x0,10 then ADD x2,x1,x1: when ADD reaches EX, ADDI is sitting in MEM. The value it computed already exists — the ALU produced it last cycle — it just hasn't reached the register file yet. So a mux steals it directly from the MEM-stage pipeline register into this cycle's EX-stage ALU input. Free: no stall, no lost cycle.

Priority matters when two producers match in the same cycle (three dependent instructions in a row): MEM is checked before WB, because if both match, MEM is the more recent value.

Load-use hazard — stall it

Forwarding moves data that already exists. A load's result doesn't exist until it reaches MEM — one stage later than EX/MEM forwarding can supply. LW x8,0(x6) followed immediately by ADDI x9,x8,1 cannot be fixed by any mux: the pipeline freezes PCF and IF/ID for exactly one cycle and injects a bubble into ID/EX, so the dependent instruction re-enters EX one cycle later — by which time the load has reached MEM and ordinary forwarding covers it.

Control hazard — flush it

The pipeline fetches sequentially, always. When a branch is taken, whatever it already fetched behind it is simply wrong, and has to be turned into a bubble before it can do any damage. See Chapter 04 for the branch-vs-JAL comparison and exactly which bubbles get injected where.

Chapter 04

Inside hazard_unit.sv

This is the one file to actually understand line by line. Everything else in the pipeline is comparatively mechanical wiring around it — and three of the project's real bugs lived here or in the file it depends on.

Forwarding — the priority encoder

// hazard_unit.sv
always_comb begin
  if      (RegWriteM && (RdM != 0) && (RdM == Rs1E)) SelectAE = FWD_MEM;
  else if (RegWriteW && (RdW != 0) && (RdW == Rs1E)) SelectAE = FWD_WB;
  else                                                 SelectAE = FWD_NONE;
  // identical block for Rs2E -> SelectBE
end

Read it as: “the instruction in EX wants Rs1E. Is anyone ahead of it about to produce that register?” Three conditions, each load-bearing:

  • RegWriteM — does the MEM-stage instruction actually write a register? A store or branch doesn't; its RdM field still holds bits (immediate bits, not a register index), so without this you'd forward garbage.
  • RdM != 0 — x0 is hardwired to zero. An instruction “writing” x0 is architecturally a no-op and must never satisfy a real dependency — there is a directed test for exactly this.
  • RdM == Rs1E — the actual match.

The if/else if order is not cosmetic: with three dependent instructions in a row, both conditions can match the same cycle, and MEM has to win because it holds the more recent value.

encodingsourcemeaning
2'b00 — FWD_NONERD1E / RD2Eordinary regfile read is fine
2'b01 — FWD_WBResultWforward from the instruction in WB
2'b10 — FWD_MEMALUResultMforward from the instruction in MEM

That encoding is counter-intuitive on purpose — M is checked first in priority but encoded second in value — and it's exactly the kind of gap that produces a real bug: a mux3 selects its first input on select 00, second on 01, third on 10, so the forwarding mux in datapath.sv has to be wired (RD1E, ResultW, ALUResultM) — WB before MEM, matching the encoding, not the priority. During original construction this was wired in the "obvious" order instead (RD1E, ALUResultM, ResultW), silently swapping the two forwarding sources. Right argument count, right names, wrong order — no compile error, and invisible on any hazard-free program. That is precisely why the directed hazard test forces an MEM-forward and a WB-forward in the same cycle for two different operands.

The load-use stall, and a subtler bug next to it

// hazard_unit.sv
assign lwStallD = IsLoadE && (RdE != 0) &&
                  ((Rs1UsedD && (RdE == Rs1D)) || (Rs2UsedD && (RdE == Rs2D)));

Rs1UsedD/Rs2UsedD exist because an instruction word is not self-describing: JAL, LUI, and AUIPC reuse exactly the same bit positions (InstrD[19:15], [24:20]) as immediate bits, not register indices. Without gating, a JAL whose immediate happened to numerically collide with a preceding load's destination register would spuriously stall — and worse, StallF freezing PCF the same cycle the JAL needs to redirect it would silently drop the jump. controller.sv's decode now emits these per opcode (and, in the CSR milestone, the *I immediate CSR variants get the identical treatment — see controller.sv's comment on Rs1UsedD).

Three flushes, three different reasons

// hazard_unit.sv, current (post-fix)
assign FlushD = PCSrcE | JumpD | EnterDebug | ExitDebug | trap_en | mret_enE;
assign FlushE = PCSrcE | lwStallD | EnterDebug | ExitDebug | trap_en | mret_enE;
assign FlushM = EnterDebug | trap_en;

FlushD and FlushE share almost the same term list because they answer the same question — “did something just redirect the PC?” — and that list is effectively a checklist: every legal way the PC can change other than +4 has to appear in both. ExitDebug was missing from it until this session; see Chapter 08, bug 2, for what that actually broke.

FlushM is the odd one out, and it's worth understanding why it has no branch-misprediction term: when a branch resolves in EX, nothing wrong-path has reached EX yet — the wrong instructions are still behind it, in D and about to enter E. So FlushM only needs two triggers, and they answer a different question — “must the EX-stage instruction's own commit be suppressed?”:

  • A trap means the EX-stage instruction is the faulting one — it must never write a register or memory.
  • Debug entry is asynchronous and can land on a perfectly correct instruction sitting in EX; it gets squashed and re-executes cleanly after resume, since dpc = PCE is its own PC.

And correspondingly, mret and dret are deliberately absent from FlushM — like a taken branch, they're pure control transfers with no register or memory write of their own to suppress. Adding them would squash an innocent instruction for no reason.

Chapter 05

Traps and CSRs

This is the one idea in the whole design that most cleanly separates “memorized the CSR encodings” from “actually understands precise interrupts.”

Two families, one hardware mechanism

Exception (synchronous)Interrupt (asynchronous)
caused byan instruction — this instructionsomething external
examples hereillegal opcode, ecall, misaligned addrCLINT timer
reproducible?yes, deterministicallyno
mepc points at…an instruction that could not completean instruction that has not run yet

Every trap, of either family, does the same four things in hardware (csr_file.sv):

mepc         <= trap_pc                    // PC of the trapping instruction
mcause       <= {trap_is_int, 26'b0, trap_cause}
mstatus.MPIE <= mstatus.MIE                 // remember whether interrupts were on
mstatus.MIE  <= 0                           // off during the handler
PC           <= mtvec

And mret undoes exactly that — PC <= mepc; mstatus.MIE <= mstatus.MPIE. Note MIE/MPIE is a one-deep stack: real nested-interrupt support needs software discipline this hardware doesn't provide, which is a fair scope line for an M-mode-only core.

The asymmetry

An exception handler must do mepc += 4. An interrupt handler must not. Same CSR, same mret, opposite treatment, and the reason is entirely in the table above.

What the pipeline adds on top

In a single-cycle core this is straightforward; in this 5-stage pipeline four things get genuinely hard:

  • Which PC? Five instructions are in flight; the trap needs the PC of the specific one that faulted. Exceptions are detected in EX, so mepc gets PCE.
  • The faulting instruction must not commit. FlushM, fired by trap_en, squashes the EX→MEM register before its RegWrite/MemWrite can land anywhere real.
  • A bubble must never be interruptible. The subtlest one. validE is 0 exactly when EX holds a flush-inserted bubble; the timer-interrupt check is gated on it, because interrupting a bubble would latch mepc = 0 (a bubble has no meaningful PC) and mret would restart the entire program.
  • CSR writes commit at EX, one stage earlier than dmem's registered MEM-stage commit — legal because only one instruction ever occupies EX per cycle, so there's no write-after-write risk, but it means the squash can't ride the usual later pipeline register; it has to be gated explicitly at the source: csr_we_gated = ctrlE.is_csr & ~EnterDebug & ~trap_en. Any future CSR-writing code path has to remember this gate, or it silently reintroduces the debug-preemption bug it exists to prevent.

The proof, in one register

tb_pipe_csr's program sets mtimecmp = 0 so the timer is pending immediately, enables interrupts, and the very next instruction is addi x25, x0, 0x555. The handler bumps a counter, defers mtimecmp far into the future (so mret restoring MIE doesn't immediately re-trigger the same interrupt), and returns without touching mepc. Three outcomes, one register:

Behaviorx25
correct — preempted instruction re-executes0x555
handler wrongly did mepc += 40x000
mepc captured the wrong PCsomething else, or never terminates

The core's real, Spike-verified run lands at x25 = 0x555 and mcause = 0x80000007 — bit 31 set (interrupt), cause code 7 (INT_MTIMER).

Chapter 06

The debug module

Halt/resume support existed before the pipeline did — debug_fsm.sv was, for a long time, literally the same file from the original single-cycle tutorial with not one line edited. That specific claim no longer holds byte-for-byte: a later style-guide retrofit (see Chapter 12) converted its two bare state constants to a typedef enum, same encoding, same behavior. What mattered every step before that, and still matters, is that the FSM's logic never changed. What changed is everything around it, because the pipeline has four candidate PCs at any instant instead of one.

The FSM's contract is simple: given a pc snapshot and an enter_debug/ exit_debug pulse, it tracks halted/running state, latches dpc = pc on entry, and tells the datapath where to redirect fetch. The design decision was which PC to feed it: PCE, the EX-stage PC — and to treat entering debug as squashing the two youngest in-flight instructions (D and E) while letting whatever's already in M and W finish normally, since they're already committed.

The PC mux carries a priority ladder above everything else discussed so far: EnterDebug > ExitDebug > trap_en > mret_enE > PCSrcE > JumpD > sequential — a halt request wins over a simultaneously-resolving branch or trap.

The bug this session found lived exactly at the seam between this chapter and Chapter 04: ExitDebug (a dret resuming the core) redirects PCNextF to dpc in the fetch mux, but hazard_unit.sv's flush terms didn't include it. The two instructions already fetched sequentially behind the dret executed for real after resume — see Chapter 08, bug 2, for the full story and why only one of the two simulators caught it.

Chapter 07

Why a self-written model can't verify itself

This chapter exists because of a real objection raised mid-project: a hand-written C++ instruction-set simulator was the golden model for a long time. Was that a legitimate reference?

The rule

A golden model is only valid for bugs whose cause it cannot share with the design. Split the old ISS's coverage against that rule and it comes out cleanly in two:

  • Microarchitecture — genuinely independent. The ISS had no pipeline at all, so it structurally could not share a hazard bug with a 5-stage pipeline. Both real RTL bugs in Chapter 08 were caught this way, and that isn't luck — it's the only bug class this arrangement can ever catch.
  • ISA semantics — close to worthless as an independent check. Same author, same reading of the spec, on both sides. The original design guide even says so without flagging it as a problem: the ISS was extended to have "the same CSR addresses, same mcause encoding, same trap priority" as the RTL. Written that way, the golden model is a restatement of the design under test — any misreading of the privileged spec sits in both files and the comparison passes.

What the swap to Spike actually found: nothing, and that's the useful result

Spike reproduces the old ISS's golden values exactly — all 32 registers plus both memory words on the hazard test, and all 32 registers on the CSR test, including the four trap counters, mcause = 0x80000007, and x25 = 0x555. The old ISS was right about everything these programs exercise. What changed isn't the numbers — it's that they're now checkable instead of assumed, and every future test program gets checked against an authority nobody on this project wrote.

One thing Spike's disassembly-level cross-check did catch, for free: the deliberate “illegal instruction” test value 0x0000007F is not an unallocated opcode as its own comment claimed — bits [6:0] = 0b1111111 is the RISC-V instruction-length encoding for instructions ≥80 bits. The test still does something valid (this core has no variable-length instruction support, so trapping is correct), but it isn't testing what its comment says, and a self-written ISS could never have revealed that — both sides agreed by construction.

Bug 1 — distance-3 RAW hazard reads a stale register

RTL
Symptom tb_pipe_hazard failed: x12 = 0x55, expected 0x77.
Root cause forwarding covers distance 1–2 relative to a consumer in EX; at distance 3 the producer is in WB while the consumer is still in ID, one stage earlier than any forwarding path reaches. See Fig. 2.

Why it's the most severe finding distance-3 dependencies are what ordinary compiled code looks like — not a corner case.

Bug 2 — dret never flushed the instructions behind it

RTL
Symptom tb_pipe_debug failed under Icarus: x1 not advancing after resume.
Root cause ExitDebug missing from FlushD/ FlushE — see Chapter 04/06.
The two-simulator argument, concretely re-seeding this bug on purpose: Icarus fails it; Verilator passes it anyway. Verilator reads uninitialised imem as 0, which is an illegal opcode, so the core trapped to mtvec = 0 (the top of the program) and accidentally fell back into the loop. Icarus is 4-state: the stray fetches read X, the PC went X, the core visibly wedged. A single simulator's initialization policy is a silent assumption in every result it gives you.

Testbench sampled one delta-cycle too early

testbench
Symptom x22 and x25 read as their reset value right after regeneration; looked exactly like a real mismatch, including on the interrupt marker register.
Root cause the last instruction before EBREAK commits its register write as a nonblocking assignment on the very edge the testbench sampled — it read the array before that write had been scheduled.
Fix a #1 after the edge.

Register file has no reset — and the two simulators disagree about that

testbench
What correct hardware (RISC-V defines no reset value for x1–x31), but a 4-state and a 2-state simulator read an unwritten register differently: X vs 0. Fixed by forcing the DUT to a known all-zero start state from the testbench — a testbench concern, not an RTL one; adding a register-file reset would be inventing hardware to satisfy a simulator.

Generated program overwrote itself (Spike is von Neumann, the DUT is Harvard)

generator
Symptom gen_stream.py: “spike never retired the sentinel”.
Root cause generated stores used a base pointer seeded to 0. The DUT is Harvard (separate imem/dmem, both based at 0) so this is harmless there; Spike has one address space, so the stores overwrote the program itself, Spike executed the corrupted bytes, trapped to an uninitialized mtvec = 0, and looped forever.
Fix the data window is now placed past the end of the program image.
Why it took a random generator every hand-written directed test respects this invariant by construction — a human never thinks to store over the code they just wrote. A random generator has no such instinct.

Spike's own boot ROM leaked into the trace

generator
Symptom the script exited 0 — and the trace was still wrong. First five rows sat at PC 0x40001000.
Root cause Spike runs auipc/addi/csrrs mhartid/lw/jalr before jumping to the ELF entry; the DUT has no boot ROM and resets straight to PC 0. Worse, that sequence leaves x11 holding a device-tree pointer — any generated instruction reading x11 before writing it would have diverged for a reason with nothing to do with the DUT, and would have looked exactly like a forwarding bug.
Fix a prologue zeros x2–x30, and the boot-ROM retirements are trimmed from the trace before comparison.
Caught by reading the actual output, not the exit code. A script that exits 0 is not the same claim as a script that did the right thing.
Chapter 09

Reading a waveform

A primer, then the real data captured from this core.

The vocabulary

  • Rising-edge sampling. Every register in this design updates on posedge clk. A signal's value between two edges is what matters; transitions mid-cycle are combinational settling, not new state.
  • X means unknown, not zero. A 4-state simulator (Icarus) will show x for any bit that has never been driven to a known value — that's not a bug indicator by itself, but see Chapter 08 for how relying on it (or on a 2-state simulator silently reading 0 instead) produced real divergences.
  • A stall looks like a repeated value. When StallF/StallD assert, PCF and InstrD hold their previous value for an extra edge instead of advancing.
  • A flush looks like a value jumping to 0x00000013 — the real NOP encoding this design uses for injected bubbles, deliberately not all-zeros (which decodes as a LOAD and would do something).
  • A forward looks like a value arriving one cycle before the register file could have supplied it — the whole reason forwarding exists.

Chapter 12

The lowRISC style retrofit

A pass applying lowRISC's Verilog Coding Style Guide to every file in rtl/. The mechanical edits are the least interesting part — what's worth understanding is where the guide's rules ran into a decision this project had already made and defended, and the call on each.

What changed

  • unique case added to every case statement (one missing default: added along the way).
  • Every module's port-list declaration reformatted to the guide's Verilog-2001 layout.
  • Tunable parameters renamed to UpperCamelCase: TESTFILE→ TestFile, MEM_WORDS→MemWords, MEM_BYTES→MemBytes, RAM_BYTES→RamBytes, WIDTH→Width — every call site updated, including the three testbench instantiations and the UVM backdoor bind.
  • debug_fsm.sv's two bare state parameters became a proper typedef enum (state_e, StRunning/StParked), same encoding, same behavior — see Chapter 06's updated note.
  • alu.sv/extend.sv's unreachable-case defaults changed from 32'bx to 32'b0: the guide is explicit that RTL must never assert X as a "don't care."
  • Opcode/ALU-control/CSR-address constants in rv32i_pkg.sv needed no change — the guide prefers ALL_CAPS for exactly that category (enumerated value constants), which is what the project already used.
  • Named-port instantiation and lower_snake_case instance names were already fully compliant throughout — nothing to change there.

What was deliberately not done

Two of the guide's rules were audited, flagged, and put to the project owner as an explicit choice rather than applied blind — because both would mean discarding a different, already-justified convention rather than fixing an oversight. Both were kept as-is, confirmed:

  • Full lower_snake_case signal renaming. This project uses Harris & Harris's pipeline-stage-suffix convention (PCF, InstrD, ALUResultE) specifically because, with five instructions in flight at once, the suffix is how you avoid confusing which instruction a signal belongs to — see Chapter 01. lowRISC's _d/_q register-pair convention is built for a single register, not a 5-deep pipeline. Swapping one deliberate naming scheme for another needed a decision, not a blind rename across every file, every testbench hierarchical path, and the wave-capture script's signal list.
  • Active-low async reset. The guide wants rst_n, active-low. This core's reset is active-high throughout, inherited from the original tutorial. Inverting it means flipping the sense of every reset condition in every sequential block in every file, plus every testbench's reset sequence — a single missed inversion is a bug that silently holds the core permanently in or out of reset.
Unverified

This entire pass was made without a working shell in the session it was done — edited by hand against the RTL as read, not compiled. debug_fsm.sv is the one file every earlier chapter holds up specifically because it was untouched since the original tutorial; that specific claim no longer holds byte-for-byte (see Chapter 06). The change there is small and mechanical, but "small and mechanical" is exactly the category this project has repeatedly found real bugs in by actually running it (Chapter 08). Run the regression (cd rtl && ./run_sim.sh) before trusting this chapter's changes.
